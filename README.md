# tauri-tate-editor

形態素解析による文体マーカーつきの、小説執筆用の縦書きエディタ。

副詞・形容詞・形容動詞に自動でマーカーを引き、推敲を支援することを目的とする。原稿用紙のマス目表示と、判型（文庫・新書など）に応じたページ区切りに対応する。

> **このリポジトリのコードは、Anthropic の Claude Opus 5 が作成しました。**
> 仕様の決定・動作確認・採否の判断は作者（TY17）が行っています。
> 各コミットには `Co-Authored-By: Claude Opus 5` を記載しています。

**操作方法は [docs/guide.md](docs/guide.md) にまとめてある。**
この README はプロジェクトの構成と、設計の理由・実測の記録を書く場所。

## 構成

| | |
|---|---|
| フレームワーク | Tauri 2（WebView2 / Chromium） |
| フロントエンド | TypeScript（vanilla・Vite） |

| 形態素解析 | Lindera 6 + SudachiDict（埋め込み） |
| 段落管理 | thunderdome（世代付きアリーナ） |

```
src-tauri/src/

  document.rs   本文の正本。Arena<Paragraph> で段落を管理
  analyzer.rs   Lindera のラッパー
src/
  main.ts       画面の組み立てとイベント配線
  editor/
    types.ts    Rust と受け渡しする型
    dom.ts      contenteditable の構造維持・キャレット制御
    session.ts  DOM と Rust の同期、解析の依頼
    marker.ts   CSS Custom Highlight API による品詞マーカー
    grid.ts     判型・マス目・文字の正規化
    scroll.ts   縦書きのホイール変換とページ送り
```

## 開発

```bash
npm install
npm run tauri dev
```

初回の `cargo build` は SudachiDict を埋め込むため非常に時間がかかり、`target/` は数 GB になる。

辞書を UniDic から SudachiDict に切り替えてある。SudachiDict は語ごとに
同義語グループ番号（details 末尾の `synonym_group_ids`）を持つ辞書系列で、
のちに類義語検索を同じ辞書で実装するための布石。品詞体系は UniDic 系
（形容動詞は「形状詞」）のままなので、マーカーの判定はそのまま使える。
ただし **details の並びが UniDic と 1 つずれる**。SudachiDict では先頭が
表示表層で、品詞大分類は 2 番目（`analyzer.rs` の `from_details`）。

```bash
cd src-tauri
cargo test
```

フロントエンドだけを素のブラウザで試すときは、`npm run dev` を起動して
`http://localhost:1420/tp-check.html` を開く。Tauri の IPC を JS で
まねた検証ページで、記法はカクヨム相当・解析は空を返す。
index.html の部品を変えたら、このページも合わせること。

## 設計上の要点

### 段落を単位にする

本文は段落の配列として持つ。差分解析・マーカーの再生成・将来の Undo が、すべて同じ単位で揃うため。

正本は Rust 側の `Arena<Paragraph>`。フロントエンドは表示用のミラーを持つだけ。打鍵のたびに IPC を往復させず、入力が止まってから（250ms）まとめて送る。

`Document::set_text` は「同じ位置に同じ本文の段落があれば `Index` と解析結果を引き継ぐ」ため、全文を送っても再解析されるのは編集された段落だけで済む。フロントエンド側で差分を計算する必要がない。

### 段落 ID を IPC に載せるときの注意

`thunderdome::Index::to_bits()` の u64 をそのまま JSON の数値として渡すと、JavaScript の Number（IEEE754 double）では下位ビットが落ちる。`to_bits` は上位 32bit にスロット番号を置くため、この精度落ちの範囲に容易に入る。

そのため `{ slot: u32, gen: u32 }` に分けて受け渡ししている（`document::ParaId`）。

### 投稿記法

ルビと傍点の書き方は投稿先ごとに違うので、相互に変換できるようにしてある。
仕様は `notation.rs` の先頭にまとめてあり、実際のサイトと食い違っていたら
そこを直せば全体に反映される。

| 記法 | ルビ | 傍点 |
|---|---|---|
| 小説家になろう | `\|漢字《かんじ》` / `漢字《かんじ》` | なし |
| カクヨム | `\|漢字《かんじ》` / `漢字《かんじ》` | `《《文字》》` |
| 青空文庫 | `｜漢字《かんじ》` / `漢字《かんじ》` | `［＃「文字」に傍点］` |
| pixiv | `[[rb:漢字 > かんじ]]` | なし |

読み込みでは「漢字の直後に《》」の形も受けるが、書き出しでは常に縦棒を付ける。
どこからルビが始まるかが曖昧にならないようにするため。ただし**記法を変えていない
本文には手を触れない**。プレビューの部品（`pieces`）は元の行から切り出した文字列を
そのまま持つので、開いただけで縦棒が増えることはない。

青空文庫の傍点 `絶対に［＃「絶対に」に傍点］` は「注記の直前にある同じ文字列に
傍点を振る」という書き方。注記だけを傍点として読むと、親文字が本文に残ったまま
傍点も出て二重になるため、直前の文字列ごと一つの傍点として読む。直前が注記の
指す文字列と違うときは、掛かる先を決められないので注記を文字のまま残す。

傍点の書き方がない記法（なろう・pixiv）では、親文字と同じ字数の中黒を
ルビとして振って代用する（`|絶対に《・・・》`）。投稿先で傍点として読める
書き方で、読み取りでもこの形を傍点として受けるので、**記法を移しても傍点は
消えない**。カクヨム → なろう → カクヨム と往復すれば元の書き方に戻る。

字数の合わない中黒（`|絶対に《・》` など）は傍点のつもりではないとみなして
ルビのまま扱う。本来の傍点の書き方がある記法（カクヨム・青空文庫）では、
中黒のルビを傍点に読み替えない。

### 表示モード

`Ctrl+E` で「記法」と「プレビュー」を切り替える。どちらでも本文を編集できる。

ルビの読み（`rt`）は絶対配置で親文字の脇へ置く。そのまま流し込むと、読みが
親文字より長いときに親文字の字送りが広がり、さらに行そのものが太って後ろの
列まで動く（実測では 20字20行で 12px ずれた）。流れから外せば、読みの長さは
組版に一切影響しない。読みの文字サイズを大きくするとその分だけ隣の行に
掛かるので、0.5em のままにしてある。

プレビューではルビと傍点を実際の形で見せる。**プレビューのままルビも直せる。**
親文字と傍点は普通の文字として置いてあり、打ち替えると記法テキストが組み立て
直される。親文字を空にすれば塊ごと消える。読みだけは `Ctrl+R` の小窓から
入れる（`<rt>` の中では日本語入力が続かないため）。

塊は `data-src`（元の行から切り出した記法）と、そのとき表示した `data-text` /
`data-ruby` を持つ。本文へ戻すときは、中身がこれらと同じなら `data-src` を
**そのまま**使う。原文に手を触れないためで、これがないとプレビューを開いた
だけで縦棒を省いたルビ `漢字《かんじ》` が `|漢字《かんじ》` に書き換わる。
手が入っていれば、Rust から受け取った型紙（`notation_forms`）で組み立て直す。
書き方の定義を画面側にも書くと Rust の表と食い違うので、必ず取りに行く。

Enter や貼り付けは Range で切り出して段落を割る。段落の中身を `textContent` で
組み直してはいけない。プレビューでは `textContent` にルビの読みまで入っており、
組み直すと読みが本文に混ざってルビが消える。ルビの中で Enter を押したときは、
記法が二つに割れないよう塊の後ろを切れ目にする。

キャレットがルビの境目にあるとき、打った文字が親文字に取り込まれることがある。
インラインで直せることと引き換えの制約で、外に出したいときは一度ルビの外へ
キャレットを動かしてから打つ。

行頭の見出し記号（`#` の並び）はプレビューでは見えなくする。要素そのものは
`visibility: hidden` で置いたままにしてある。消してしまうと、以降の文字が
記法表示とは違うマスに来て、マス目と揃わなくなるため。

傍点に品詞マーカーが掛かるときだけは、ハイライトを使わず**塊の中で語を
`span` で囲み、要素の色で示す**。ゴマ点は文字の枠の外（縦書きなら右脇）に
描かれるので、そこへハイライトや傍線を重ねると点が潰れて読めなくなる。
要素の背景は文字の枠の中しか塗らないため、点には掛からない。

塊まるごとを色付けしてはいけない。解析した語と対応しなくなり、記法表示と
見え方が食い違う（`《《まだ誰にも見せたくなかった》》` なら、記法表示では
「まだ」と「なかっ」だけに印が付く）。`segment.ts` が塊の中の位置まで返し、
`sidemark.ts` がその範囲だけを囲む。

塊の中を囲むと DOM が変わるのでキャレットが飛ぶ。描き直しで実際に書き換えた
ときだけ、選択範囲を文字数で覚えて戻す。始点だけを戻すと、傍点を付けた直後に
選び直した範囲が畳まれてしまう。

**品詞マーカーはプレビューでも出る。** Rust が返すオフセットは記法テキストの
上での位置なので、段落の中身を `segment.ts` で「記法テキストのどこに当たるか」の
区間の並びに直してから DOM に写す。ルビや傍点の塊は途中で切れないので、
掛かったときは塊ごと引く（ルビの読みには引かない）。記法の記号だけに掛かる
マーカーは、見えている語と対応しないので捨てる。

### プレビューでの削除 ─ まず注記から外す

プレビューでの削除はブラウザに任せない。ブラウザの既定の削除は、
ルビや見出し記号の塊を半端に壊したり、段落の結合で要素を複製したり
して、読み戻した記法が崩れる（見出しやルビのある行を消すとルビが
壊れることがあった）。`beforeinput` の delete 系をすべて横取りする
（`session.ts` の `handleDelete`）。

消し方は「まず注記から」。

- ルビや傍点の塊に**外から**削除が触れたら、一度目は注記だけを外す。
  ルビは読みが外れて親文字が残り、傍点は点が外れて文字が残る。
  見出し記号は記号そのものが注記なので丸ごと消える（見出しでなくなる）。
  もう一度消せば、ふつうの文字として消えていく。
  消しすぎて本文まで失うことがないし、半端に壊れた記法も残らない
- キャレットはクリックや矢印移動で塊の「**中の端**」に立つことが多い。
  端に立って塊の中身へ向かう削除も、塊への削除として扱う。ここを
  見ないと、注記より先に親文字が消えてしまう。端から塊の外へ向かう
  削除は自前で 1 文字だけ消す（ブラウザに任せると外の文字を塊の中へ
  引き込むことがある）
- 塊の**中ほど**にキャレットがあるとき（親文字の打ち替え）は、
  ふつうの文字消しとしてブラウザに任せる
- 段落の先頭での Backspace（前の段落との結合）と選択範囲の削除は、
  記法テキストを繋ぎ直してから段落を組み立て直す。塊の一部にしか
  掛かっていない選択は塊の全体まで広がる（`srcOffsetAt` の約束）ので、
  記法が途中で切れることはない

### プレビューの元に戻す・やり直す

プレビューの Ctrl+Z / Ctrl+Y は**自前の履歴**で行う（記法表示は
今までどおりブラウザの履歴）。プレビューの編集の多くは段落を自前で
組み直すためブラウザの履歴に載らず、載っている分だけ戻すと組み直す
前の古い DOM が甦って記法が壊れる。

1 段は「本文（記法テキスト）＋選択位置」の複製。編集を加える**前**に
積む。打鍵と文字消しは間が空くまでひとまとめ、改行・貼り付け・IME の
変換・ルビや傍点の操作はそれぞれひと区切りとして積む。戻すときは
正本（Rust）を戻してから段落を組み直す。

Ctrl+Z は `beforeinput` の historyUndo では受けられない。ブラウザ側の
履歴が空だと**そもそも発火しない**ので、keydown の段階で受ける。
本文の差し替え・表示モードや記法の切り替えで履歴は捨てる。

### ルビと傍点の入力の設計

操作は使い方ガイドを参照。設計上の要点は三つ。

**読みは本文に直接打たせない。** `<rt>` の中では日本語入力が続かず、変換を
始めた時点で入力が外れてしまう。ふつうの `input` なら IME がそのまま効くので、
読みの入力だけを小窓（本文の外）へ出してある。親文字と傍点は本文で
直接打ち替えられる。

選んだところがルビや傍点に半端に掛かっているときは、その塊ごと選んだもの
として扱う（記法は途中で切れない）。ルビを含む範囲に傍点は付けられない。
行頭の見出し記号には掛からない（掛けると見出しでなくなる）。

段落の書き換えは Rust の `toggle_emphasis` が行う。掛かっていない部分は
元の記法をそのまま写すので、縦棒を省いたルビなどが巻き添えで書き換わる
ことはない。

### 文体の指摘

`stats.rs` が品詞マーカーと同じ解析結果を使い回して、推敲の手がかりを出す。
指摘の種類と既定のしきい値は使い方ガイドを参照。しきい値は
`localStorage` に残し、範囲外の値は読み出し時に丸める。

文末の連続は**段落をまたいで**数える。小説では段落が短く、段落ごとに区切ると
「〜た。」の連続を取りこぼすため。

使いすぎは千字あたりの回数で見る。分量の違う原稿を並べても比べられる。

### 見出し

行頭の `＃` の連続を見出しとみなす。数を増やすと下の階層になる。
半角の `#` も認識するが、**半角文字は半角幅で描画されるため、その行だけ升からずれる**。
案内では全角を勧めている。本文の行頭は常に升に揃うので、ずれは見出し行の中だけで収まる。

章別の文字数は「その見出しから、同じか浅いレベルの次の見出しまで」を数える。
下位の見出しの分も含むので、章のすぐ下に節を置いても章の分量が 0 にならない。

### 組版の自動化

文字サイズと行送りのつまみは無くした。どちらも**1 行の字数から自動で
決まる**。

- 字送り（文字サイズ）: 1 行がちょうど画面の高さに収まる大きさ。
  字数の多い判型（文庫の 42 字など）ほど文字が小さくなる。実際の
  文庫本も 1 行が長い分だけ文字が小さい
- 行送り: 字送りの `STEP_RATIO`（1.7）倍。行間（字の箱どうしの空き）が
  0.7em でき、ルビ（0.5em）と傍点の丸がそこへ収まる。1.5 を切ると
  ルビが前の行の字に乗るので、比はこの余裕を持たせて決めてある。
  さらに保険として、読みの文字サイズは
  `min(0.5em, 行間 - 1px)` にしてあり、行間が狭くなっても読みが
  行間からはみ出ることはない

### 書体の選択

書体はインストール済みのフォントから選ぶ。一覧は Rust（fontdb）で
列挙し、**日本語のグリフを持つ書体だけ**を返す。持っているかどうかは
名前では分からないので、実際にフォントを開いて cmap を引く
（ひらがなと漢字を 1 字ずつ。ファミリーごとに最初の 1 面だけ）。
表示名は日本語のファミリー名があればそちらを使う。

選んだ書体には半角固定のフォールバック（TateHalf*）を前置して
スタックを組む。ゴシック系の名前ならゴシックの半角、それ以外は
明朝の半角。

**升に乗るかどうかは表ではなく実測で調べる**（`isGridSafeFont`）。
何が来るか分からないので、選んだ書体で実際に組んで、全角が 1em・
半角が 0.5em で送られるかを測る。仮名が詰まるプロポーショナル書体
（BIZ UDP 系・MS P 系など）はここで弾かれて警告になる。

覚えていた書体がアンインストールされていたら既定（MS 明朝）に戻す。

### 組版の数値の決め方

数値の決め方には二つの罠があった。

- **行間を半端な値にしない。** `行送り = round(字送り × 1.7)` のような
  決め方だと行間（片側 = (行送り−字送り)/2）が 5.5px などになり、
  マス目の 3 層のグラデーションの境界が半画素ずつずれて歪んで見える。
  行間そのものを丸め、行送りは「字送り + 行間 × 2」で組み立てる。
  さらに Windows の拡大率（125% など）では CSS px の整数も端末画素で
  半端になるので、字送りも行間も `1 / devicePixelRatio` の刻みに乗せる
- **グリッドの行は明示的に割り当てる。** `.app` は
  `grid-template-rows: auto auto 1fr auto` だが、検索バーが
  `display: none` で抜けると自動配置では後続が一行ずつ繰り上がり、
  本文が auto 行・ステータスバーが 1fr 行に入る。本文の高さが中身なり
  になってウィンドウを広げても追従せず、下に大きな空きができていた

用紙が画面より狭いときは**右端へ寄せる**（縦書きの原稿は右端の行から
始まる）。`viewport` を flex にして用紙に `margin-left: auto` を
当てるだけで、用紙が画面からあふれると auto は 0 になり、ふつうの
横スクロールに戻る。

### 類義語検索

操作は使い方ガイドを参照（`Ctrl+Q`）。

キーの割り当てには制約がある。**`Ctrl+T` は使えない**。WebView2 が
ブラウザ側のアクセラレータ（タブ操作系。Ctrl+T / Ctrl+N / Ctrl+W）
として飲み込んでしまい、ページに keydown が届かない。Ctrl+R や
Ctrl+B のようなページ配達されるキーとは扱いが違う。

候補は三段で出す。

- **言い換え** … Sudachi 同義語辞書（`src-tauri/assets/synonyms.txt`、
  Apache License 2.0）。厳密な同義語で、グループは小さい。
  SudachiDict の synonym_group_ids からグループ番号を取り、番号→語は
  埋め込んだ辞書で解決する。番号が取れない語でも見出しの完全一致
  （表層と正規化形の両方）で引ける
- **同義** … 日本語 WordNet（`src-tauri/assets/wnjpn-ok.tab`、
  再配布可・`wnja-LICENSE.txt` を同梱）。語を概念（synset）で
  まとめた約 5.7 万概念・9.4 万語のデータで、類語辞典らしい広さは
  こちらが担う。多義語は概念ごとにグループが分かれる
- **近い意味** … WordNet の概念のつながりをたどった語。上位・下位の
  概念と、形容詞の類似（sim）の語。つながりは wnjpn.db から抜き出した
  `wnjpn-links.tsv`（日本語の語を持つ概念どうしに絞ってある）を使う

活用した語（「歩い」）も、SudachiDict の正規化形（歩く）を鍵に
WordNet が引ける。一度出した語は別の段に重ねて出さない。

キャレット位置から引くときは行を分かち書きして、その位置に掛かる
内容語を探す（助詞・助動詞・記号は飛ばす）。多義語はグループごとに
区切りを入れて出す。誤表記として登録されている語（展開制御フラグ 2）
は提案に出さない。

### 表記ゆれ検出

「子供／子ども」「頂く／いただく」のような同じ語の表記の混在を、
文体パネルに「表記ゆれ」として指摘する。

SudachiDict の**正規化形**は語形の揺れと活用を吸収した見出しになる
（子ども→子供、頂い→頂く）。そこで「正規化形・品詞・活用」が同じ
なのに表層が違う語を揺れとみなす。活用まで鍵に入れるのは、
走る／走っ のような活用違いを揺れと取り違えないため（頂いた／
いただいた は同じ活用形なので拾える）。

語の抽出は品詞マーカーと同じ一度の分かち書きで済ませ、段落ごとに
キャッシュする（`analyzer::Analysis`）。助詞・助動詞・記号・数詞は
見ない。指摘は語彙素ごとに 1 件で、位置は**少ないほうの表記の初出**
に付ける（多数派に合わせて直すことが多いため）。

### 行末句読点のぶら下げ

行末に入りきらない句読点（、。）は、以前は行頭禁則で前の字ごと
次の行へ送られていた（追い出し）。いまは升の外へはみ出させて前の
行に留める（ぶら下がり組み。`editor/hang.ts`）。

CSS の `hanging-punctuation` は Chromium 148 でも未実装なので自前で
行う。升が完全等幅なことを利用する。

1. **追い出された句読点を実測で見つける。** 前の字が行頭に立って
   いて、かつ前の行にその字のぶんの空きが残っていれば、それは
   自然な折り返しではなく追い出し
2. その句読点を `letter-spacing: -1em` の span（`.hang`）で包む。
   字送りが 0 になるのでブレーカーには行に収まったと見え、
   グリフだけが升の外へはみ出してぶら下がりになる

負の `margin-inline-end` はブレーカーが折り返しの計算に入れて
くれないため使えない（実測）。letter-spacing は字送りそのものを
変えるので効く。

編集や判型の変更で折り返しが変わったら、場所の合わなくなった
ぶら下げをほどいてから探し直す（マーカーの描き直しと同じ束で走る。
IME 変換中は触らない）。ぶら下げた句読点の次が行頭禁則の字
（」や ー など）のときは、下げても崩れるので追い出しのままにする。

### 設定の永続化

判型・書体・マス目・マーカー・配色・表示モードを `localStorage` に覚えて、
次に開いたときに同じ見た目で始める（`editor/settings.ts`）。つまみを動かす
たびに書くと無駄が多いので、少し置いてからまとめて書く。

読み出したものは信用しない。手で書き換えられることもあれば、版が変わって
形が違うこともある。既定値に重ねたうえで、数は範囲へ丸め、選択肢は表にある
ものだけを通す。**壊れた設定で起動できなくなるのがいちばん困る。**
知らない書体を覚えていた場合も既定へ落とす。

記法（`notation.ts`）と文体のしきい値（`style.ts`）は、それぞれの都合が
あるので別のキーで持っている。

### 配色

白・生成り・夜の三つ。色はすべて `:root` の CSS 変数にまとめてあり、
`:root[data-theme]` で差し替える。規則の側は触らない。

品詞マーカーの色も変数にしてある。`.cls ::highlight(名前)` の形は効かない
ので配色ごとに規則を書き分けられないが、**`::highlight()` の中の `var()` は
`:root` の値を拾う**（実測で確認）。おかげでマーカーも配色に追従する。

生成りは紙の色だけを変える。夜は紙まで暗くするので、蛍光ペン（紙に重ねる
半透明）はそのまま効くが、傍線と文字色は暗い紙に暗い色では見えないため
明るい側へ振り直している。

### 印刷／PDF

見た目は `src/print.css` が決める。画面用とは別ファイルにして `media="print"`
で読ませてあり、確かめたいときは `link` の `media` を `all` にすれば画面で
そのまま見られる。

用紙は A4 横。**1行の字数から文字の大きさを決め直す**ので、画面の文字サイズ
は印刷に影響しない。画面の px をそのまま刷ると 96dpi 換算になり、判型と関係
のない大きさになってしまう。行送りは画面での比（`--step-ratio`）を保つ。

ページそのものを縦書きにする（`html, body { writing-mode: vertical-rl }`）。
本文だけが縦書きのままだと、用紙は横書きのページとして送られ、横に長い本文が
右端で切れる。

品詞マーカーと検索の強調は刷らない。色を変数にしてあるので、印刷では変数を
透明にするだけで、ハイライトも傍点の中の印もまとめて消える。マス目は刷る
（`print-color-adjust: exact` が要る）。

`--cell` と `--step` だけは `!important` が要る。画面用の値を `grid.ts` が
`:root` のインラインスタイルで入れているため、ふつうの規則では勝てない。

### 外部テキストの取り込み

貼り付けとファイル読み込みでは、必ず改行を段落に割ってから取り込む。
`contenteditable` にそのまま入れると生の改行がテキストノードに残り、
`readText` が段落を `\n` で繋ぐためモデル側で段落が余分に割れる。
青空文庫からの貼り付けで実際に起きた。CRLF と CR も同様に扱う。

読み込みの文字コードは BOM → UTF-8 → Shift_JIS → EUC-JP の順に推定する。
改行は内部では常に LF に揃え、元の改行コードは保存時に戻す。

### 文字位置の単位

Rust は UTF-8 バイト、JavaScript は UTF-16 コード単位で文字列を数える。マーカーの位置は **UTF-16 単位に変換してから** 返す（`analyzer::analyze_text`）。これを怠るとサロゲートペアを含む段落でマーカーがずれる。

## 実装前の検証で分かったこと

着手前に、素の HTML で以下を実測した（`../vertical-editor-probe.html`、`../vertical-grid-probe.html`）。

### CSS Custom Highlight API

- **DOM を書き換えないので、IME 変換中にマーカーを更新しても入力が壊れない。** span を挿す方式との決定的な違い
- `text-decoration` は `::highlight(名前)` の**単体セレクタでしか効かない**。`.クラス ::highlight(名前)` と書くと無視される（`background-color` と `color` は子孫セレクタでも効く）。そのため表示スタイルは CSS クラスではなくハイライト名で切り替えている
- `text-underline-position: right` は効かず、**傍線は必ず文字の左側**に出る
- `overline` と `text-emphasis`（傍点）は描画されない

### 縦書きのマス目と、行を太らせるもの

ルビ（`rt`）と傍点（`text-emphasis`）は、そのまま置くと**行そのものが
太って、後ろの行がマス目から外れる**。字の外側に出るぶんの場所を行が
確保しようとするため。実測では字送り 40px・行送り 48px で、傍点ひとつ
につき 16px ずれた。行送りを広げれば収まるが、行送りは書く人が決める
ものなので、組版の側で吸収しなければならない。

どちらも**絶対配置で流れから外す**。ルビは `rt` を、傍点は文字ごとの
入れ物（`.bt`）の疑似要素を使う。傍点を塊ごと疑似要素にすると、行を
またいで折り返したときに点の位置が合わなくなるので 1 文字ずつにする。

**傍点の点は `text-emphasis` に描かせず、自分で丸を置く。**
`text-emphasis` の点は字の外へ 0.5em ほど張り出す。流れの中ならその
ぶん行が太って収まるが、行を太らせないために絶対配置にした箱には
張り出す余地がなく、点が字に重なる。箱を広げれば重ならないが、今度は
行送りが詰まっているときに隣の行の字へ乗る（字送り40px・行送り48px
なら 20px はみ出す）。行間に収まる大きさの丸（`--dot`）を置けば、
行送りをいくつにしても隣とぶつからず、行も太らない。点は行間に
合わせて 2px〜0.22em のあいだで育つ。

升目は「行の帯」ではなく「文字の箱」に合わせて引く。縦書きの字は行の
帯（`--step`）の真ん中に置かれるので、帯の端に線を引くと字と線のあいだ
に半行ぶんの空きができ、升が字を掴んでいないように見える。余った左右
の空きはルビと傍点が出る場所で、原稿用紙の行間と同じ役目をする。

### 縦書きのマス目

- **禁則処理はマス目を壊さない。** 19 字の行ができても次の行はまた升の先頭から始まるので、行末に空きマスができるだけ。原稿用紙として正常な見た目であり、自前で行分割を実装する必要はない
- マス目を壊すのは**半角幅で描画される文字**だけ。`—`(U+2014 EM DASH) は MS 明朝・BIZ UD 明朝で半角になる。小説のダーシは `―`(U+2015) を使えば揃う（`grid.normalizeText` で置換）
- 游明朝の約物（、。「」）が詰まる原因は書体ではなく **Chromium の
  `text-spacing-trim` の既定値**だった。Chromium は halt/vhal を持つ書体
  （游明朝・游ゴシック）の約物を既定で半角へ詰める。MS 系はこの
  フィーチャーを持たないので影響がなく、「游だけ詰まる」ように見えて
  いた。`text-spacing-trim: space-all` で止めれば游明朝も升に乗る
  （`font-feature-settings: "palt" 0` では防げない。palt とは別物）。
  和欧間に 1/8em を差し込む `text-autospace` も升を割るので
  `no-autospace` で止める
- 半角英数の幅は書体ごとにまちまち（游明朝の英数はプロポーショナル）。
  **半角の範囲（U+0020-007E と半角カナ）だけ MS 明朝／MS ゴシックへ
  振り向ける `@font-face` の `unicode-range`** で、どの書体でも半角を
  ちょうど 0.5em（1 マスに 2 字）に固定した（styles.css の TateHalf*）。
  全書体で全角 1em・半角 0.5em が揃うことを実測で確認済み
- `hanging-punctuation` は Chromium 非対応。句読点のぶら下げ組みはできない

### スクロール

- Chromium は縦書き要素の上でも**縦ホイールを横スクロールに変換しない**。自前で `wheel` を横取りする必要がある
- `scrollLeft` の原点と符号が環境によって異なる。`scrollIntoView({inline:"start"})` も期待どおりに動かない。
  そこで起動時に「`scrollLeft` を増やすと中身が画面上でどちらへ何 px 動くか」を実測し、以降はその比率で換算している（`scroll.ts` の `calibrate`）。画面上の座標だけで考えられるので、原点や符号の違いを意識しなくて済む
- **縦書きの CSS multicol はページ送りに使えない。** 段が上下に積まれる新聞レイアウトになる。ページ区切りは背景の `repeating-linear-gradient` で描く
